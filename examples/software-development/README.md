# ソフトウェア開発への適用

題材：トークンの有効期限と現在時刻が等しい場合を「期限切れ」にする、境界条件の修正。実サービスの認証実装ではなく、検証手順を再現できる小さな例です。

## Understand

- 目的・成果：`is_expired(expires_at, now)` が期限の前でFalse、同時と後でTrueとなるコードとテスト。
- 完了条件：この3条件を自動テストで確認する。APIの引数・戻り値は維持する。
- 範囲：同一時間基準の整数時刻の比較。署名検証、時計のずれ、外部サービス統合は対象外。
- 許可：この例のローカル編集・テスト。実サービス、本番書込、マージ・デプロイは許可に含まない。
- 役割：AIが実装・検証・報告。依頼者が目的と受容判断、運用責任者が必要な本番操作の承認を担う。
- Core：[共通契約](../../core/contract.md)と[共通ライフサイクル](../../core/lifecycle.md)。用途別に変更しない。
- Practices：[tdd](../../practices/tdd.md)、[security](../../practices/security.md)。Git利用は本例の前提ではないためpre-commitは未選択。

## Act / Verify

[修正前](before/expiry.py)は `>` を使うため、同時刻のテストに失敗します。[修正後](expiry.py)は `>=` を使います。同じ[3テスト](test_expiry.py)を修正前後へ適用します。

```sh
python3 -m unittest discover -s examples/software-development -p 'test_*.py' -v
```

修正前の再現も含めるには、ルートで `python3 scripts/verify.py` を実行します。修正前コードと同じテストを一時ディレクトリへコピーして実行するため、成果物を壊さずに失敗を再現できます。修正前の1失敗は期待した不具合再現、修正後の3成功が受入根拠です。

## Adapt

修正前の失敗時点では完了にしません。[失敗時の状態](status-failed.md)から境界比較を調べ、修正後の結果を確認して[完了状態](task-status.md)へ移ります。実行記録は[検証ログ](../../docs/verification.txt)を参照します。

本番適用まで依頼が拡大した場合は別の権限判断です。[承認待ちの例](status-approval.md)で、必要な判断を明示します。シナリオ内の承認は実際に得たものではありません。
